# 나들이 6인 테스트 적용 메모

실행 화면은 `front/public/moov.html`입니다. `front/app.js`는 현재 첫 화면에서 사용되지 않습니다.

## 실행

1. 백엔드: `cd backend` 후 `python -m pip install -r requirements.txt`, `python -m uvicorn main:app --reload --port 8000`
2. 프런트: `cd front` 후 `npm run dev` (`http://localhost:3000`)
3. `GET http://localhost:3000/api/outing/health`에서 저장소 종류를 확인합니다.

로컬 `localhost` 화면은 `127.0.0.1:8000` 백엔드로 직접 요청합니다. 다른 호스트에서 열린 화면은 같은 출처의 `/api/outing/*`를 사용하고, `front/server.mjs`가 백엔드로 전달합니다. 다른 서버에서 백엔드를 운영하면 프런트 서버에 `MOOV_BACKEND_URL`을 설정합니다. 정적 호스팅에서는 `/api/outing/*` 역방향 프록시를 별도로 구성하거나 `window.MOOV_OUTING_API_BASE`를 화면 스크립트 전에 설정해야 합니다.

## 팀 공용 저장소

기본값은 `backend/.outing-events.sqlite3`로, **이 PC에서만** 기록됩니다. 팀원 6명이 같은 로그를 보려면 백엔드 환경변수 `MOOV_OUTING_DATABASE_URL`에 팀 PostgreSQL 연결 문자열을 설정하고, 모두 같은 백엔드로 접속해야 합니다. 이 값은 Git에 넣지 않습니다. 현재 프로젝트 `.env`에는 이 설정이 없어서 공용 DB 검증은 아직 하지 못했습니다. 프로토타입 로그인 ID는 인증이 아니므로 실제 개인정보는 입력하지 마세요.

로그는 고정 `user_id`(로그인 ID), 브라우저 세션 ID, 추천 요청 ID, 고유 이벤트 ID, 발생/수신 시각, 선택 조건과 추천 규칙 버전을 저장합니다. 프런트가 오프라인일 때는 사용자별 브라우저 큐에 남겨 같은 ID로 재전송합니다. 백엔드는 중복 ID를 무시합니다. 테스트 모드는 `지정 시나리오`와 `자유 사용`으로 구분합니다.

## 6인 확인 순서

각자 **서로 다른 고정 로그인 ID**를 쓰고, 지정 시나리오 6개를 2회씩 수행하면 72회 추천 세션입니다.

1. CATEGORY를 카페·음식점·전시 등으로 바꿔 후보와 순위를 확인합니다.
2. 같은 CATEGORY에서 분위기·동행·시간대·참고 예산만 바꿉니다.
3. 검색 결과가 없거나 조건이 충돌할 때 빈 결과와 조건 변경 안내를 확인합니다.
4. 상세 보기, 저장, 저장 취소, 좋아요, 좋아요 취소를 수행합니다.
5. 다시 추천하고 다른 화면을 다녀온 뒤 입력값과 새 요청 ID를 확인합니다.
6. 새로고침·로그아웃·다른 ID 로그인 후 나들이 기록이 섞이지 않는지 확인합니다.

## 데이터 해석

현재 15개 코스의 CATEGORY·가격·거리·일부 좌표는 검수 전 데모 데이터입니다. 추천 점수는 코스 수준의 임시 태그 일치 점수이며 만족 확률이나 장소별 일치율이 아닙니다. 가격에는 이동비가 검증되어 있지 않고, 영업시간과 실제 예약 가능 시간도 검증되지 않습니다. 좌표가 없는 장소에는 임의 위치를 만들지 않습니다. 최근 7일 인기순은 백엔드에 기록된 유효 좋아요만 사용하며 기존 예시 좋아요 숫자는 제외합니다.

실제 가격·영업시간·장소 좌표·렌트 시간 정책이 확정되기 전에는 예산/시간 충족이나 실제 방문을 보장하지 않습니다. 6명 테스트는 기능·기록 품질을 확인하는 과정이며 일반 사용자 취향을 대표하는 학습 데이터로 취급하지 않습니다.
